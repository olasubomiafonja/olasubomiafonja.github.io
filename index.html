01 / 05Biometrics · Onboarding

Face search: one face, many accounts

Live in production
Objective
Stop one person from opening several accounts under different identities, borrowing on each and defaulting on all of them.
Audience
The credit and onboarding teams, whose loan book carried these losses, and the fraud desk that reviews flagged cases.
Idea & reasoning
Defaulted accounts kept showing the same person under new names, phones and IDs. Those are cheap to change. A face isn't, so every new selfie should be searched against existing customers.
Tools & process
Reviewed defaulted cases to confirm the pattern, wrote the requirements, agreed the match threshold and review rules with engineering, and designed the reviewer screen.
Deliverable
An automatic face search at onboarding, plus a "Resolve face search match" screen where an analyst compares the two accounts side by side and records a decision in one click.
Outcome · measured
1,000+face search blocks in one quarter
~97.5%upheld on review
Beforeany money goes out
Only about 2.5% of blocks were cleared as false positives on review. Many flagged applicants were people who had already defaulted under another identity, so loans that would likely have been lost were never disbursed.
My contributionSpotted the multi-account pattern in defaulted loans, proposed face search, set the match threshold and the three review outcomes, designed the review screen, led testing, and own the review process.
Engineering contributionBuilt the biometric search service, wired it into onboarding and built the review screen.

Logic I specified · illustrative Python: duplicate-face check 
# Illustrative only: a simplified version of the idea, not production code.
import numpy as np

MATCH_THRESHOLD = 0.90   # tuned against reviewed cases

def cosine(a, b):
    return float(np.dot(a, b) / (np.linalg.norm(a) * np.linalg.norm(b)))

def screen_new_selfie(applicant, face_index):
    """Compare a new applicant's face against every existing customer."""
    hits = []
    for customer in face_index.nearest(applicant.embedding, k=20):
        score = cosine(applicant.embedding, customer.embedding)
        same_person = score >= MATCH_THRESHOLD
        different_identity = customer.id_number != applicant.id_number
        if same_person and different_identity:
            hits.append((customer.user_id, round(score, 2)))

    if hits:
        return {"decision": "HOLD_FOR_REVIEW", "matches": hits}
    return {"decision": "PASS"}
02 / 05Compliance · Automation

NIBSS watchlist management

Live in production
Objective
Act on every BVN in the industry fraud watchlist quickly, accurately and with an audit trail.
Audience
Fraud analysts doing the work, the compliance team, and regulators (CBN, NIBSS) who expect timely action.
Idea & reasoning
Watchlist files hold thousands of BVNs and matching them by hand took days, while a known fraudster could still transact. Each category maps to one clear action, so the work could be automated.
Tools & process
Mapped each category to an action: watchlisted means a PND (Post No Debit), deceased means the account is closed, and delisted means it's reactivated. Then wrote the spec and tested it with engineering and compliance.
Deliverable
A watchlist page in the fraud console. An analyst uploads the NIBSS file, and every matched account gets a PND, is closed or is reactivated automatically, with upload history and per-file results.
Outcome · measured
8,500+customers matched since Apr 2025
448K+records screened across 60+ files
61K+account actions (PND, close, reactivate)
~4 minper file
At even one minute per action by hand, that's roughly 1,000 analyst hours saved (estimate).

Logic I specified · illustrative SQL: watchlist matching 
-- Illustrative only: generic table names, simplified logic.
WITH watchlist AS (
  SELECT bvn, category, requesting_bank
  FROM staged_watchlist_upload            -- the file just uploaded
),
matched AS (
  SELECT c.customer_id, c.account_status, w.category
  FROM customers c
  JOIN watchlist w ON w.bvn = c.bvn
)
SELECT
  customer_id,
  category,
  CASE
    WHEN category = 'fraud'       THEN 'PLACE_PND'      -- Post No Debit
    WHEN category = 'deceased'    THEN 'CLOSE_ACCOUNT'
    WHEN category = 'delisted'
     AND account_status = 'watchlist_pnd'    THEN 'LIFT_PND'
  END AS action
FROM matched;

Fraud management system

Live in production
Objective
Bring detection, investigation and decisions into one console, so fraud is caught in real time and every case has one owner, one status and one history.
Audience
Fraud analysts and transaction monitoring, the compliance team, leadership, and auditors or law enforcement who ask for evidence later.
Idea & reasoning
Alerts came from different places and cases lived in sheets and chats, so analysts lost time and decisions were hard to explain. Putting the rules, the queue and the evidence in one place, with AI doing the reading, lets analysts spend their time on judgement.
How rules and AI are built in
Rules engine: each rule is a set of conditions (amount, account age, velocity, device, beneficiary) with an action and a severity. Every alert shows exactly which rule fired. New rules are tested on past data before they go live, so we know their hit rate and precision up front.
AI copilot: on every case, AI summarises the account's activity, explains why it looks risky, finds similar past cases, suggests a next step and drafts the regulatory report narrative. The analyst always makes the final decision.
Deliverable
A fraud console with an overview dashboard, alert queue, rules engine, case workspace with AI copilot, NIBSS watchlist and reports.
Outcome
Alerts, rules and cases now live in one place with a full audit trail. AI summaries and draft narratives cut the reading and writing in each case, so analysts move faster and decisions are more consistent. Detailed performance figures are internal and not quoted here.
My contributionDesigned the case workflow and stages, wrote the detection rules and thresholds, chose where AI should help analysts, wrote the requirements and led testing. My team works in it daily.

Logic I specified · illustrative Python: case lifecycle 
# Illustrative only: a case can only move along allowed paths.
ALLOWED = {
    "NEW":           {"INVESTIGATING"},
    "INVESTIGATING": {"CONFIRMED", "CLEARED"},
    "CONFIRMED":     {"ACTIONED"},
    "CLEARED":       {"CLOSED"},
    "ACTIONED":      {"CLOSED"},
}

def move_case(case, new_status, analyst, note):
    if new_status not in ALLOWED[case.status]:
        raise ValueError(f"Can't go from {case.status} to {new_status}")
    if not note:
        raise ValueError("Every decision needs a reason")
    case.history.append((case.status, new_status, analyst, note))
    case.status = new_status
04 / 05Account takeover · KYC

Closing the face-swap loophole

Live in production
Objective
Detect and stop account takeover (ATO): a fraudster gets into a genuine customer's account, fails the face check, then passes on a second try using the real owner's face.
Audience
The fraud desk investigating account takeover, the KYC operations team and the product owners for onboarding and verification.
Idea & reasoning
Reviewing rejected selfies, I saw accounts with two different faces minutes apart: the fraudster's own face, rejected, then the real owner's face (from a photo or the owner themselves), accepted. The face check looks at one selfie at a time, so it can't see the switch, and the takeover goes through.
Tools & process
Gathered takeover cases from rejection reviews, wrote the rule and its edge cases (same person in different light vs. a different person), and worked through them with engineering.
Deliverable
A face history check: every new selfie is compared with all earlier selfies on the same account, including rejected ones. If they're different people, the account is held for review.
Outcome
Takeover attempts that would pass a single face check are now caught and held before the fraudster can move money or take a loan in the victim's name.
My contributionLinked the face switch to account takeover while reviewing rejected cases, defined the rule and its edge cases, and led testing.
Engineering contributionBuilt the face history comparison into the onboarding flow.

Logic I specified · illustrative Python: face history check 
# Illustrative only.
SAME_PERSON = 0.85

def check_face_history(account, new_selfie):
    """Flag when a newly accepted face is a different person from earlier faces."""
    previous = [f for f in account.faces if f.id != new_selfie.id]
    for old in previous:
        score = similarity(old.embedding, new_selfie.embedding)
        if score < SAME_PERSON:
            return {
                "decision": "HOLD_FOR_REVIEW",
                "reason": "multiple_faces_on_account",
                "earlier_face_status": old.status,   # e.g. rejected
                "score": round(score, 2),
            }
    return {"decision": "PASS"}

Query pattern I use · illustrative SQL: monthly summary 
-- Illustrative only: generic schema.
SELECT
  DATE_TRUNC('month', f.flagged_at)                    AS month,
  f.control_name,                                          -- face_search, watchlist, ...
  COUNT(DISTINCT f.customer_id)                           AS customers_caught,
  SUM(CASE WHEN l.disbursed_at < f.flagged_at
           THEN l.outstanding ELSE 0 END)               AS exposure_at_flag,
  SUM(CASE WHEN l.disbursed_at IS NULL
           THEN a.requested_amount ELSE 0 END)          AS loans_prevented
FROM fraud_flags f
LEFT JOIN loans l             ON l.customer_id = f.customer_id
LEFT JOIN loan_applications a ON a.customer_id = f.customer_id
GROUP BY 1, 2
ORDER BY 1, 2;
